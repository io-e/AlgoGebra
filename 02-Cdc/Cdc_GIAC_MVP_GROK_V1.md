## 1. What the source note got right

- Desktop GIAC is JNI. The Java side is the package `javagiac` in `source/shared/giac-jni/src/main/java/javagiac/`.
- Those Java files are generated by SWIG 1.3.40. `giacJNI.java` says so. Do not edit them by hand.
- The call shape is string in, `gen` evaluation, string out: `new_gen__SWIG_25(String, context)`, `gen_eval`, `gen_print__SWIG_0`.
- Natives ship as OS-specific jars. At runtime the DLL is extracted and loaded with `System.load` on an absolute path. Upstream desktop does this in `org.geogebra.desktop.cas.giac.NativeLibClassPathLoader`, called from `CASgiacD`.
- The RCP product must not use boot delegation. The accepted loaders are the three fragments under `03-RCP-Spike/host/`.

## 2. What the source note got wrong or overreached

- This GeoGebra checkout does not contain the GIAC C++ sources. `giac-jni` is the Java wrapper plus a Gradle task that unzips prebuilt native jars. Reviewing "the C++ in GeoGebra" here will not find the engine.
- The C++ , the SWIG interface, and the Emscripten build live in the separate GeoGebra GIAC mirror, `https://github.com/geogebra/giac`, not in this tree. That repo was not re-audited for this note.
- The web half of the note is not an MVP requirement. This project's browser client is still the GWT build until Gate C. There is no `giac.js` integration to copy inside the RCP spike.
- `NativeLibClassPathLoader` is not the RCP loader. D-05 accepted `GiacNativeBootstrap` as the permanent Equinox replacement. It must keep living outside `common`.
- Only the GIAC bootstrap falls back from the application class loader to the bundle class loader. JOGL and GlueGen do not. Native jars stay on the application classpath.
- The Gradle comment in `giac-jni/build.gradle.kts` says the unzip task fully supports Linux only. Windows still works through the product fragments. Do not treat that comment as "Windows GIAC is absent".

## 3. MVP

One desktop call, on the already built Windows RCP image.

**In.** A single Xcas string, for example `Expand[(x+1)^2]`.

**Out.** The printed GIAC string, for example `x^2+2x+1`, plus an error string if GIAC rejects the input.

**Must.**

- Start from `Launch-Strict-Native-Gate.cmd`. No `-BootDelegateJogAmp`, no `-ManualNativeFallback`.
- Load `javagiac64.dll` through `GiacNativeBootstrap` in the GIAC JNI bundle class space.
- Use one `javagiac.context` per evaluation. Do not keep a global context in the host.
- Call the existing SWIG entry points. Do not add a JNI method and do not compile GIAC.
- Leave `source/shared/common` unchanged.
- Return the result to the GeoGebraPlus host as text. Do not insert an `AlgoElement`.

**Must not, in this MVP.**

- Rebuild GIAC from C++.
- Add WebAssembly or replace GWT.
- Expose the full GeoGebra CAS view as a new API.
- Load Linux or macOS `.so` / `.dylib` files. Those are a later row, not this pass.

## 4. Done when

On Windows 11 amd64, Java 25, Equinox 3.24.300, one strict launch log shows:

1. `javagiac64.dll` loaded by absolute path.
2. `Expand[(x+1)^2]` returns `x^2+2x+1`.
3. `1+1` returns `2`.
4. A bad input returns an error to the host and does not kill the RCP process.

The log `rcp-20261029-073727-5656-eee96ccd` already shows 1–3. The remaining MVP gap is item 4 and a host method with a name, instead of the reflection adapter inside the spike.

## 5. Next slice, after the MVP

A host interface `evaluate(String command) -> String`, implemented only on desktop, with the error case tested. Web GIAC stays out until Gate C chooses a browser runtime.
