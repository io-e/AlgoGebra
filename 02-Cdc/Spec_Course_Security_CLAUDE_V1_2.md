## 0. Threat model

A course file (`course.json`) is **untrusted data** authored by teachers or generated by tools (e.g., OEF converter). It may be served by a WIMS instance the student does not control. A malicious or buggy course file must not:

1. Execute arbitrary code on the student's machine
2. Read or write files outside the course sandbox
3. Corrupt the GeoGebra construction state in unrecoverable ways
4. Produce an authoritative grade in the browser (grades are WIMS server-side only)

## 1. Command validation — allowlist, not denylist

### 1.1 Why denylist fails

The V1_1 study proposed a denylist of command name strings (`Execute`, `System`, `Shell`, etc.). This is broken:

- **Localized names:** GeoGebra commands are translated. French users type "Exécute" for `Execute`. The denylist checked English strings only.
- **Nesting:** `Sequence(Execute("malicious"), k, 1, 5)` passes a string-level denylist because `Execute` is inside a `Sequence` argument.
- **Phantom names:** `System`, `Shell`, `Exec`, `JsEval`, `JavaScript`, `RunMacro` are not in the `Commands` enum — listing them is misleading.
- **New commands:** any command added in a future GeoGebra version would be allowed by default.

### 1.2 Allowlist design — post-parse check

The course executor validates commands **after** GeoGebra's parser has resolved them to `Commands` enum values (or rejected them as invalid syntax). This makes the check immune to localization and nesting.

#### Allowed command categories

The `Commands` enum assigns each command to a table constant. The allowlist permits entire categories:

| Table | Allowed | Rationale |
|---|---|---|
| `TABLE_GEOMETRY` | **Yes** | Core construction commands (Point, Line, Circle, Polygon, etc.) |
| `TABLE_ALGEBRA` | **Yes** | Algebraic operations (Solve, Factor, Expand, etc.) |
| `TABLE_TEXT` | **Yes** | Text display (Text, LaTeX, FormulaText, etc.) |
| `TABLE_LOGICAL` | **Yes** | Boolean operations (If, IsDefined, etc.) |
| `TABLE_FUNCTION` | **Yes** | Function definition and evaluation |
| `TABLE_CONIC` | **Yes** | Conic sections |
| `TABLE_LIST` | **Yes** | List operations (Sequence, Join, Sort, etc.) |
| `TABLE_VECTOR_MATRIX` | **Yes** | Vector and matrix operations |
| `TABLE_TRANSFORMATION` | **Yes** | Geometric transformations |
| `TABLE_CHART` | **Yes** | Statistical charts |
| `TABLE_STATISTICS` | **Yes** | Statistical functions |
| `TABLE_PROBABILITY` | **Yes** | Probability distributions |
| `TABLE_SPREADSHEET` | **Yes** | Spreadsheet operations |
| `TABLE_SCRIPTING` | **NO** | Script execution: `Execute`, `RunClickScript`, `RunUpdateScript`, `ExportImage`, `StartRecord`, `PlaySound`, `ReadText`, etc. |
| `TABLE_DISCRETE` | **Yes** | Discrete math |
| `TABLE_GEO_PROOFS` | **Yes** | Prover commands |
| `TABLE_CAS` | **Yes** | CAS commands |
| `TABLE_OPTIMIZATION` | **Yes** | Optimization commands |
| `TABLE_3D` | **Yes** | 3D commands (Point3D, Plane, Sphere, etc.) |
| `TABLE_FINANCIAL` | **Yes** | Financial functions |

#### Individual command overrides

Even within allowed categories, these specific commands are **blocked** because they have side effects beyond construction:

| Command | Table | Reason |
|---|---|---|
| `Delete` | SCRIPTING | Removes objects — could undo teacher-set construction |
| `SetValue` | SCRIPTING | Modifying existing objects is allowed only through the schema's explicit `VAL` directive with a named variable |
| `Rename` | SCRIPTING | Renaming objects breaks references |
| `Pan`, `ZoomIn`, `ZoomOut`, `CenterView` | SCRIPTING | View manipulation — confusing for students |
| `SetPerspective` | SCRIPTING | Layout change — host-owned |

#### Explicitly allowed scripting commands

These `TABLE_SCRIPTING` commands are safe and useful for courses:

| Command | Reason |
|---|---|
| `SetColor` | Visual styling for step feedback |
| `SetPointStyle`, `SetPointSize` | Visual styling |
| `SetLineThickness`, `SetLineStyle` | Visual styling |
| `SetCaption` | Adding labels |
| `ShowLabel` | Display control |
| `SetFixed` | Preventing student modification of teacher objects |
| `Slider` | Creating interactive parameters |
| `Checkbox` | Creating toggles |

### 1.3 Implementation — RCP (Java)

```java
// In DirectiveExecutor.java (post-parse validation in StepValidator)
import org.geogebra.common.kernel.commands.Commands;

private static final Set<Integer> BLOCKED_TABLES = Set.of(
    Commands.TABLE_SCRIPTING
);

private static final Set<Commands> BLOCKED_COMMANDS = Set.of(
    Commands.Delete, Commands.Rename,
    Commands.Pan, Commands.ZoomIn, Commands.ZoomOut,
    Commands.CenterView, Commands.SetPerspective
);

private static final Set<Commands> ALLOWED_SCRIPTING = Set.of(
    Commands.SetColor, Commands.SetPointStyle, Commands.SetPointSize,
    Commands.SetLineThickness, Commands.SetLineStyle,
    Commands.SetCaption, Commands.ShowLabel,
    Commands.SetFixed, Commands.Slider, Commands.Checkbox
);

boolean isCommandAllowed(Commands cmd) {
    if (BLOCKED_COMMANDS.contains(cmd)) return false;
    if (ALLOWED_SCRIPTING.contains(cmd)) return true;
    return !BLOCKED_TABLES.contains(cmd.getTable());
}
```

The check runs **after** the parser has resolved the command name to a `Commands` enum value. Localized names ("Exécute") resolve to `Commands.Execute`, which is in `TABLE_SCRIPTING` and not in `ALLOWED_SCRIPTING` — correctly blocked.

### 1.4 Implementation — Web (JavaScript)

The web client cannot inspect the `Commands` enum at runtime. Instead:

1. The host page maintains a **string allowlist** of internal command names (English, matching the enum).
2. Before `evalCommand(str)`, the course-tree.js extracts the command name from the input string and checks the allowlist.
3. The allowlist is generated from the Java enum during build and shipped as a JSON file (`allowed-commands.json`).

**Limitation:** the web check is on the raw input string, not the parsed command. A localized command name not in the allowlist would be rejected (safe default), but nesting is harder to detect. Since web grading is not authoritative (WIMS server re-checks), this is an acceptable defense.

## 2. OPEN action — file path validation

The `OPEN` directive loads a `.ggb` file into the GeoGebra applet.

### 2.1 Allowed path

The resolved path must be **under the course directory** (the directory containing the `course.json` file).

```java
// V1_2: toRealPath() resolves symlinks (SEC-G3 settled)
Path resolved = courseDir.resolve(openPath).toRealPath();
Path realCourseDir = courseDir.toRealPath();
if (!resolved.startsWith(realCourseDir)) {
    throw new SecurityException("OPEN path escapes course directory: " + openPath);
}
```

### 2.2 Rejected patterns

| Pattern | Example | Reason |
|---|---|---|
| `..` | `../../etc/passwd` | Path traversal |
| Absolute path | `/tmp/evil.ggb` or `C:\evil.ggb` | Escapes course directory |
| URL | `http://evil.com/payload.ggb` | Remote file loading |
| Non-`.ggb` extension | `exploit.jar` | Only `.ggb` files allowed |

### 2.3 Web OPEN

On the web client, `OPEN` translates to `ggbApplet.setBase64(content)` where content is fetched from a relative URL. The `fetch()` URL must be relative and must not contain `..` or start with `//`, `http:`, or `https:`.

### 2.4 Untrusted OPEN — fail-closed pre-scanner (V1_2, owner Q2)

**Until the `.ggb` script scanner (WP9-04) is implemented, all `OPEN` actions without explicit `trustedGgb: true` are REJECTED.** This is a fail-closed default: the validator cannot verify that an untrusted `.ggb` is safe without the scanner.

After the scanner exists:
- A clean in-course `.ggb` (no script elements, no blocked commands) → `ACCEPT`
- A `.ggb` with script content → `REJECT` (unless `trustedGgb: true`)

### 2.5 SEC-G3 — Symlink resolution (V1_2, errata settled)

**Decision: Option A (strict).**

- **Desktop (RCP):** `toRealPath()` is **mandatory** before the path-prefix check. `normalize()` alone does not resolve symlinks and is insufficient. A symlink inside the course directory pointing to `/etc/passwd` or any file outside the course root must be caught.
- **Web:** Browser `fetch()` of a relative URL does not resolve OS symlinks. Protection is server-side:
  1. The **publish pipeline** (when packaging course assets for serving) must reject symlinks and non-regular files.
  2. The **HTTP server** must not follow symlinks outside the document root (e.g., `Options -FollowSymLinks` on Apache, or equivalent).
  3. The student browser only sees same-origin relative paths; it cannot create OS-level symlinks.

**Test:** T-27 — symlink inside course dir pointing outside → REJECT.

## 3. `.ggb` archive scanning

A `.ggb` file is a ZIP archive. It can contain:

| File in archive | Risk | Check |
|---|---|---|
| `geogebra.xml` | Construction XML — may contain `<command>` elements | Scan for blocked commands (same allowlist as §1) |
| `geogebra_javascript.js` | **Global JavaScript executed on load** | **Must be empty or absent.** Reject the file if this entry contains any code. |
| Per-object `onUpdate`, `onClick`, `onMouseDown` script attributes in `geogebra.xml` | Script execution per object | Scan all `<element>` nodes for `<script>` or `<javascript>` child elements. Reject if any are found (unless `trustedGgb: true`). |
| `<ggbscript val="…">` elements in `geogebra.xml` | **Inline GeoGebra script blocks** | Scan for `<ggbscript` elements (see §3.1). |
| `geogebra_defaults2d.xml`, `geogebra_defaults3d.xml` | Styling defaults | Safe — no code execution |
| `geogebra_macro.xml` | Macro definitions | Scan for blocked commands within macro definitions |
| Image files (`.png`, `.svg`) | Embedded images | Safe |

### 3.1 SEC-G1 — `<ggbscript val="…">` handling (V1_2, errata settled)

**Decision: Option A (strict) — reject any `<ggbscript` element unless `trustedGgb: true`.**

GeoGebra uses `<ggbscript val="…">` elements in `geogebra.xml` to attach commands to object events (update, click). These are functionally equivalent to `<javascript>` handlers: they can execute any GeoGebra command, including blocked ones like `Execute` or `Delete`.

**Rationale for strict rejection:** Parsing the `val` attribute and applying the command allowlist (Option B) would require replicating the GeoGebra command parser in the scanner context, handling localization, nesting, and expression evaluation. This is fragile and expands the attack surface. Since `<ggbscript>` is a scripting mechanism, the safe default is to treat it like any other script element.

**Implementation:**

```java
private static boolean containsScriptElements(String xml) {
    return xml.contains("<javascript")
        || xml.contains("<script")
        || xml.contains("<ggbscript")
        || xml.matches("(?s).*on(Update|Click|MouseDown)\\s*=.*");
}
```

The scanner checks for the `<ggbscript` **element open tag**, which catches both `<ggbscript val="...">` (attribute form) and `<ggbscript>...</ggbscript>` (element form). No separate attribute-specific check is needed.

**Tests:** T-15 (`<ggbscript val="Execute(...)">` → REJECT), T-29 (`<ggbscript val="Execute(...)">` per-object → REJECT), T-30 (`<ggbscript onUpdate>` → REJECT).

### 3.2 Scanning implementation (RCP)

```java
// GgbScriptScanner.java (WP9-04)
public class GgbScriptScanner {

    public static ScanResult scan(Path ggbFile) throws IOException {
        try (ZipFile zip = new ZipFile(ggbFile.toFile())) {
            // Check geogebra_javascript.js
            ZipEntry jsEntry = zip.getEntry("geogebra_javascript.js");
            if (jsEntry != null && jsEntry.getSize() > 0) {
                String js = readEntry(zip, jsEntry).strip();
                if (!js.isEmpty()) {
                    return ScanResult.rejected("geogebra_javascript.js contains code");
                }
            }

            // Check geogebra.xml for script attributes
            ZipEntry xmlEntry = zip.getEntry("geogebra.xml");
            if (xmlEntry != null) {
                String xml = readEntry(zip, xmlEntry);
                if (containsScriptElements(xml)) {
                    return ScanResult.rejected("geogebra.xml contains script elements");
                }
                List<String> blockedFound = findBlockedCommands(xml);
                if (!blockedFound.isEmpty()) {
                    return ScanResult.rejected("Blocked commands: " + blockedFound);
                }
            }

            // Check macros
            ZipEntry macroEntry = zip.getEntry("geogebra_macro.xml");
            if (macroEntry != null) {
                String macroXml = readEntry(zip, macroEntry);
                List<String> blockedFound = findBlockedCommands(macroXml);
                if (!blockedFound.isEmpty()) {
                    return ScanResult.rejected("Blocked commands in macros: " + blockedFound);
                }
            }

            return ScanResult.accepted();
        }
    }
}
```

### 3.3 `trustedGgb` flag

A course file can mark specific `.ggb` files as trusted:

```json
{
  "directive": "OPEN",
  "value": "construction_with_scripts.ggb",
  "trustedGgb": true
}
```

This flag means the teacher accepts the embedded scripts. The host **must display a visible warning** when loading a trusted `.ggb` file (owner Q4 — `ACCEPT_WITH_WARNING` result). In a WIMS context, the server should validate the `.ggb` before making it available.

A trusted OPEN that passes path rules → `ACCEPT_WITH_WARNING`. The warning is visible to the user and logged, but does not block loading. **A warning never overrides a REJECT**: if the same step contains a trusted OPEN *and* a blocked command, the step result is `REJECT` (T-55).

## 4. Validation result states (V1_2, owner Q4)

### 4.1 Structured result

```java
enum Verdict { ACCEPT, ACCEPT_WITH_WARNING, REJECT }
record ValidationResult(Verdict verdict, List<String> reasons, List<String> warnings) {}
```

### 4.2 Combination rules

Results combine per-directive → per-step → per-course:

| Scenario | Result |
|---|---|
| All directives ACCEPT | `ACCEPT` |
| Any directive ACCEPT_WITH_WARNING, none REJECT | `ACCEPT_WITH_WARNING` (warnings accumulated) |
| Any directive REJECT | `REJECT` (warnings kept in log but do not appear to user as acceptance) |

**Key rule:** warnings never override a rejection. A step with both a trusted OPEN (warning) and a blocked command (rejection) produces `REJECT`.

### 4.3 CLI contract (suite 16)

Codex delivers a validator callable as `COURSE_VALIDATOR="<cmd>"`, invoked `<cmd> <course.json>`:
- First stdout token: exactly `ACCEPT`, `ACCEPT_WITH_WARNING`, or `REJECT`
- Remaining stdout: reasons and warnings (human-readable)
- Exit code: ignored (the first token is authoritative)
- Any other first token → `CONTRACT_VIOLATION` (test FAIL)

### 4.4 Grading trust boundary

```
Browser (untrusted)                    WIMS Server (trusted)
───────────────────                    ─────────────────────
  courseTree shows formative ✓/✗          Authoritative grade computation
  Student can inspect/modify JS           Server-side .ggb analysis
  Client check = hint only                Server check = the grade
```

**Rule:** never trust a grade computed in the browser. The submission step sends the construction state to WIMS, which recomputes independently.

## 5. Course file size, depth, and iteration limits (V1_2, owner Q3)

| Limit | Value | Rationale |
|---|---|---|
| Maximum `course.json` size | 1 MB | Prevents memory exhaustion |
| Maximum tree depth | 5 levels | Prevents stack overflow in recursive rendering |
| Maximum total actions | 500 | Prevents denial of service via step execution |
| Maximum `.ggb` file size | 50 MB | GeoGebra files can contain embedded images |
| Maximum `OPEN` actions per course | 10 | Limits file system access |
| Maximum iterations per `Sequence` | **1 000** (V1_2) | Prevents CPU exhaustion per individual Sequence call |
| Maximum generated items per directive | **10 000** (V1_2) | Aggregate budget across all Sequence calls in one CMD/CAS directive (nested = product of counts) |

### 5.1 Sequence budget — deterministic static analysis (V1_2, owner Q3)

**Supersedes** the V1_1 rule of "max 10,000 per Sequence". The owner decision (issue #17) tightens this to a two-level budget enforced by **static analysis at validation time**, before any GeoGebra execution.

#### Rules

1. **Bounds must be statically provable:** start, end, and step values must evaluate to numeric constants without referencing construction objects, sliders, random values, or free variables. If bounds are not statically provable → `REJECT` (reason: `sequence-bound-not-static`).

2. **Count formulas:**
   - `Sequence(n)` → count = n
   - `Sequence(expr, var, a, b)` → count = floor((b − a) / 1) + 1
   - `Sequence(expr, var, a, b, s)` → count = floor((b − a) / s) + 1; `s = 0` or wrong sign → `REJECT` (unbounded)

3. **Per-Sequence limit:** count ≤ 1 000. Over → `REJECT` (reason: `sequence-over-budget: <n> > 1000`).

4. **Per-directive limit:** sum of all generated items across all `Sequence` calls in one directive ≤ 10 000. Nested Sequences: inner count × outer count. Over → `REJECT` (reason: `directive-items <n> > 10000`).

5. **Nested bound dependency:** if inner Sequence bounds depend on the outer variable and are not still statically provable, → `REJECT`.

#### Near-limit warning — DROPPED (V1_2, owner Q3b, issue #21)

**The `SEQUENCE_WARNING_THRESHOLD = 800` near-limit warning is removed.** Sequences at or below the limits produce plain `ACCEPT`, not `ACCEPT_WITH_WARNING`. The `ACCEPT_WITH_WARNING` verdict is reserved for other Q4 uses (e.g., trusted OPEN).

**Rationale:** a valid course that uses 1000 iterations should not trigger a warning that confuses teachers or students. The hard limits are the security boundary; the warning added noise without security value.

**Test impact:** T-45 (1000 iterations) and T-51 (10×1000 in one directive) must return `ACCEPT` (not `ACCEPT_WITH_WARNING`).

#### Watchdog (optional, diagnostic only)

An optional 2-second watchdog may log slow directives (`D-xx WARN slow directive <ms>`). It must **never** interrupt, cancel, or `Thread.stop` work on the SWT/GeoGebra UI thread. It is not a security control; the static budget is.

### 5.2 Web parity

The web host (`course-tree.js`) currently enforces `MAX_SEQUENCE_ITER = 10000` (V1_1). This must be updated to match the V1_2 limits:

- Per-Sequence: 1 000
- Per-directive: 10 000

The web check is simpler (string-level, no parse tree), so it only catches the numeric end bound. This is acceptable for internal demos under the interim denylist (owner L2), since WIMS is the authoritative grader. The full post-parse budget is a desktop/server concern.
