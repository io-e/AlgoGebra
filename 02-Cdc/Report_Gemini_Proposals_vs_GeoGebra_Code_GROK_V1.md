# GROK_V1

# Gemini's proposals against the GeoGebra source

Status: draft, 2026-10-28.

Code read: `D:\ALF_ZGit\G1_Geogebra_Migration` (upstream `main`, desktop `assemble` and web `gwtCompile` already succeeded on this tree).

Gemini brief: `01-Recherche\synth_se_de_l_architecture_et_du_d_veloppement_sur_geogebra_GEM.md`.

Requirement this report answers: an architecture as flexible as Eclipse, or a move of the product into Eclipse.

## 1. What the tree actually is

The repository is one Gradle composite build, not an application platform.

| Build | Role | Runtime |
|---|---|---|
| `source/shared` | Kernel and shared libraries | Compiled into both products |
| `source/desktop` | Classic 5 Swing shell | JVM, main class `org.geogebra.desktop.GeoGebra3D`, toolchain Java 25 |
| `source/web` | Classic 6 / Suite / 3D calculator | GWT, Java source compiled to JavaScript |

`shared` projects: `common`, `common-jre`, `canvas-base`, `renderer-base`, `editor-base`, `keyboard-base`, `keyboard-scientific`, `ggbjdk`, `giac-jni`, `xr-base`.

`common` is the kernel: construction, commands, CAS glue, algebra. Its Gradle file calls it "Common parts of GeoGebra for various platforms". It is a normal Java library. It `api`-depends on the editor, the renderer, and the canvas. It is not a small stable API with the app behind it.

`desktop` projects: `desktop`, `canvas-desktop`, `editor-desktop`, `renderer-desktop`, `jogl2`. JOGL natives are copied beside the jars at `run` time because JOGL does not follow `java.library.path` or a normal classpath. The desktop jar manifest lists the whole runtime classpath in `Class-Path`.

`web` projects: `web`, `web-common`, `web-dev`, `canvas-web`, `renderer-web`, `editor-web`, `keyboard-web`, `carota-web`, `gwtutil`, `gwt-generator`. Production compile emits four GWT modules: `SuperWeb` (`war/web3d`), `WebSimple`, `Web`, `Tablet3D`. A full production compile on this machine took about 16 minutes. Dev mode is a codeserver plus a page on port 8888.

There is no `module-info.java` split, no OSGi `MANIFEST.MF` bundle set, and no `ServiceLoader` registry in the kernel. Variation between Graphing, Geometry, 3D, and Suite is a `switch` in `App.createDefaultToolCollectionFactory()` (`source/shared/common/.../main/App.java`), which constructs `GraphingToolCollectionFactory`, `GeometryToolCollectionFactory`, `Graphing3DToolCollectionFactory`, or `SuiteToolCollectionFactory`. Adding a product flavor means editing that class.

GWT modules (`*.gwt.xml`) inherit fixed source trees (`common`, canvas, editor, renderer, GWT user). A type that is not on that source path, or that uses a Java API GWT cannot translate, cannot be part of the web app. GWT has no custom class loader. A jar dropped in a folder at runtime is invisible to the web build.

The README's supported IDE is IntelliJ. `source/build-logic` contains `idea-conventions.gradle.kts`. Nothing in the build generates Eclipse plugin projects or Equinox launch configs.

## 2. What "as flexible as Eclipse" means here

Eclipse has two layers that Gemini mixes together:

1. **Equinox runtime.** Bundles, separate class loaders, extension points in `plugin.xml`, install and start without rebuilding the platform.
2. **The Eclipse IDE.** A workbench for editing and launching. That does not make the program under development modular.

GeoGebra today has neither. Gradle modules are compile-time jars. They are linked before the user starts the app. The web output is one JavaScript permutation per GWT module.

A result is flexible in the Eclipse sense only if a new feature can be added as a separate bundle, loaded by the running app, and removed without editing `App.java` or recompiling `common`. None of Gemini's options do all of that for both desktop and web.

## 3. Proposal A — web shell and the JavaScript API

Gemini's recommendation: wrap the web applet in a page (React, Vue, or plain JS) and let modules call the official JavaScript API.

**What the code supports.** The web app is already an applet with a war output (`web3d`, `webSimple`, `web`, `tablet3d`) and `deployggb.js` is generated by `mergeDeploy` in `source/web/web/build.gradle.kts`. An outer page can load a `.ggb`, read objects, set values, and eval commands. That matches GeoGebraPlus in `Cdc_Evolution_GeoGebra_GROK_V1.md`.

**What it does not support.** The API remote-controls a finished applet. It cannot register a new geometry type, a new command, or a new view inside the kernel. Those changes are described by the project's own notes `doc/dev/HowToAddANewObjectType.md`, `HowToAddANewCommand.md`, and `HowToAddANewTool.md`: edit `common`, then rebuild. On the web, "rebuild" is a GWT compile.

**Eclipse comparison.** This is an embedding API, closer to an OLE/ActiveX control than to an Eclipse extension point. Flexibility sits outside GeoGebra. The kernel stays closed.

**Fit for this project.** Good for the student page, the notebook bridge, and 2D/3D figures. Insufficient if the goal is to evolve GeoGebra itself the way Eclipse plugins evolve the workbench.

## 4. Proposal B — Java SPI (`ServiceLoader`)

Gemini: define service interfaces and load compiled implementations on the desktop.

**What the code would need.** Interfaces in a tiny module that `common` does not already implement in one class. Today the factories are concrete classes selected by `App`. A first SPI would replace that `switch` with `ServiceLoader.load(ToolCollectionFactory.class)` and, later, the same pattern for commands and object types.

**Desktop.** This works on the Classic 5 JVM. Plugins are jars on the classpath. There is no isolation: a plugin can see and break every public type in `common`. `common` exposes thousands of public classes and depends on editor, renderer, and canvas, so the "API" a plugin compiles against is the whole kernel. That is the opposite of an Eclipse extension point, which is a small schema.

**Web.** GWT does not run `ServiceLoader`. A desktop jar plugin will not appear in `SuperWeb` unless its sources are added to a `gwt.xml` and the module is recompiled. Two plugin mechanisms would exist, and only one of them would reach the browser.

**JPMS, which Gemini lists next to SPI.** The desktop launch already needs `--add-exports java.base/java.lang`, `--add-exports java.desktop/sun.awt`, `--add-exports java.desktop/sun.java2d`, and `--enable-native-access=ALL-UNNAMED`. JOGL, JNA, Rhino, and the manifest `Class-Path` assume a flat classpath. Putting `common` behind `module-info.java` collides with that, and GWT would still compile the sources as a non-modular tree. JPMS does not help the web half.

**Eclipse comparison.** SPI is a service registry, not an extension registry. No version ranges, no lazy activation, no per-plugin class loader, no declarative UI contribution.

## 5. Proposal C — PF4J

Gemini: Plugin Framework for Java, one class loader per plugin.

**Desktop only.** PF4J can wrap Classic 5 if a real plugin API is carved out of `common` first. That carve-out does not exist. Loading plugins against the current public surface means each plugin compiles against a snapshot of the whole kernel and breaks on upstream refactors.

**JOGL.** Native jars must sit next to `jogl-all` and `gluegen-rt`. A plugin class loader that hides those jars, or that loads a second copy, breaks the 3D view. Any PF4J design has to keep natives on the application class loader and document that as a hard rule.

**Web.** PF4J cannot load inside GWT. A PF4J desktop plugin is absent from the student web app.

**Eclipse comparison.** PF4J is the closest desktop-only stand-in for Equinox, with much less tooling and no UI extension model. It still leaves the web monolith untouched.

## 6. Proposal D — OSGi, Bnd, Equinox, "migrate into Eclipse"

Gemini: Gradle Bnd to emit OSGi manifests, run on Equinox, which is the base of Eclipse.

**What would have to move.**

- Each Gradle project becomes a bundle with `Import-Package` / `Export-Package`. `common` currently exports, in practice, everything. A honest OSGi split starts by choosing the few packages plugins may import. That is a multi-month cut of `common`, not a build-file change.
- Desktop Swing UI (`org.geogebra.desktop`, about 800 Java files) would become an RCP application or an Equinox-on-Swing application. RCP wants SWT. Mixing Swing views and SWT workbench parts is a permanent seam. Keeping Swing and dropping the workbench means Equinox without the Eclipse UI, so developers do not get Eclipse extension points for menus and views unless they adopt `org.eclipse.ui`.
- GWT cannot be an Equinox bundle that hot-deploys. The web compiler wants sources, not resolved OSGi wires. The shared kernel would still be compiled twice: once as bundles for the desktop, once as GWT source for the browser. Plugins written as bundles would not cross that line.
- Java 25 is required for `:desktop:run`. Eclipse releases lag current Java. An RCP port has to pin an Eclipse version that runs on 25, or lower the desktop toolchain. Both are maintenance costs against upstream.
- Upstream is IntelliJ-oriented and publishes to `repo.geogebra.net`. An Equinox fork cannot take upstream merges as a Gradle pull. Every kernel change in `common` becomes a bundle-metadata and, on the web, a GWT-compile problem.

**What "migrate into Eclipse" can honestly mean.**

| Reading | Result | Kernel plugins in the browser |
|---|---|---|
| Import the Gradle tree into the Eclipse IDE | Editing and debug only. The app is unchanged. | No |
| Desktop shell becomes an RCP app; `common` stays one jar | Eclipse UI around the same kernel. | No |
| `common` split into OSGi bundles with extension points | Desktop plugins in the Eclipse sense. | No, until a second web registry exists |
| Abandon GWT and draw with a Java UI only | One Equinox app. Loses the web student client. | Desktop only |

The requirement "as flexible as Eclipse, including the web student tool" is not met by an Equinox port of this tree. The web product and Equinox are different runtime models, and the kernel is shared source between them.

## 7. Proposal E — WebSocket or local API

Gemini: a bridge so Python or C# can drive the engine.

This is proposal A with another transport. The notebook kernel would call get, set, eval, and reset. It does not load new kernel code. It is the right bridge for Jupyter. It is not an Eclipse architecture.

A process that embeds the Java kernel (headless `common-jre`) and speaks WebSocket is possible on the desktop classpath. `common-jre` is already the headless entry used by tests. That still ships the monolith in-process. Callers do not plug in a new object type without a jar on that classpath and a code change to register it.

## 8. Comparison

| Proposal | New kernel type without editing `common` | Works in the GWT web app | Eclipse-like install/remove | Fits GeoGebraPlus + notebook | Cost on this tree |
|---|---|---|---|---|---|
| A. JS API shell | No | Yes, the shell is outside | No | Yes | Low. Page plus API. |
| B. SPI | Only if the type is already behind a loaded interface, and only on the JVM | No | Weak (classpath jars) | No for web features | Medium, and it forks the registration style. |
| C. PF4J | Desktop, after an API is carved out | No | Yes on the desktop | No | High, plus JOGL class-loader rules. |
| D. Equinox / Eclipse RCP | Desktop, after a package export cut | No | Yes on the desktop | No, unless the student app stops being GWT | Highest. Fork diverges from upstream. |
| E. WebSocket | No | As a client of the applet | No | Yes | Low, after A. |

## 9. Consequence for the requirement

Two different products are being asked for in one sentence.

**Product 1, student workspace.** Notebook for non-graphical work, GeoGebraPlus for figures, Wims and VS Code on the teacher side. Proposal A, then E, matches the code. Eclipse is the wrong runtime.

**Product 2, a GeoGebra that accepts plugins like Eclipse.** The only runtime in this repo that can host real plugins is the desktop JVM, and only after `common` grows a small exported API. The web app cannot host them without leaving GWT or generating a second, compile-time registry. A full Eclipse RCP migration buys the desktop workbench and drops or freezes the web path.

Doing both means a permanent double implementation: an Equinox extension on the desktop and a GWT or JS registration on the web, for every plugin. Upstream will not maintain that. This project would.

## 10. Questions

These decide the architecture. The report should not pick Equinox or the JS shell until they are answered.

1. Who must be able to extend GeoGebra: only this project, or teachers and third parties who never compile Java?
2. Must a new module run in the browser, or is a desktop-only plugin acceptable?
3. Name one capability the official JavaScript API cannot provide and that the first version must have. If there is none, Product 1 does not need Eclipse.
4. Does "Eclipse" mean the Equinox runtime and extension points, or the Eclipse IDE as the editor for the existing Gradle tree?
5. Is losing the GWT web app acceptable if the desktop becomes an RCP application?
6. Is a long-lived fork of `common` acceptable? Upstream merges will conflict as soon as packages are split for OSGi.
7. Are 2D and 3D the only GeoGebra surfaces, with every Algo* subject staying in the notebook, as in `Cdc_Evolution_GeoGebra_GROK_V1.md`?
8. Must plugins be loadable and removable without restarting the app, or is a rebuild per feature enough?
9. Which Eclipse release, if any, is already installed, and is Java 25 allowed for that release?
10. Should the next document be a package-level cut of `common` for a desktop extension point, or a command list for the JavaScript API of GeoGebraPlus?
